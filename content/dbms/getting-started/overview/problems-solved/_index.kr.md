Machbase DBMS는 데이터가 조용히 쌓이는 환경보다, 계속 흘러 들어오는 환경에서 진가를
발휘합니다. 예를 들어 공장의 설비 상태, 서비스의 접속 로그, 도시 인프라의 센서 값,
그리고 금융 시장의 틱 데이터처럼 시간이 지나면 금세 양이 늘어나는 데이터가 있습니다.
이런 데이터는 저장만 해서는 부족하고, 들어오는 즉시 확인하고 나중에도 다시 분석할 수
있어야 합니다.

시계열 데이터베이스가 해결하는 문제는 단순히 “많은 데이터를 저장한다”가 아닙니다. 데이터가
빠르게 들어올 때 입력을 놓치지 않아야 하고, 사용자는 방금 들어온 데이터와 오래전에 쌓인
데이터를 모두 시간 조건으로 찾아야 합니다. 또한 원본 데이터를 오래 보관할수록 저장 공간이
커지므로, 어느 시점부터 집계 데이터로 바꾸거나 보관 기간을 정하는 운영 전략도 필요합니다.

Machbase DBMS는 다음 문제가 동시에 있는 환경에 적합합니다.

- 장비, 센서, 애플리케이션, 시장 데이터 피드에서 데이터가 초 단위 이하로 계속 발생합니다.
- 최근 데이터는 즉시 조회해야 하고, 오래된 데이터도 장기 분석에 필요합니다.
- 입력 성능을 유지하면서 SQL, 집계, 조인, 보관 정책을 함께 사용해야 합니다.
- 시계열 원본 데이터와 기준 정보를 함께 다뤄야 합니다.
- 초 단위·밀리초 단위 원본 데이터와 분·시간·일 단위 집계 데이터를 함께 다뤄야 합니다.

테이블 유형은 이 문제를 나누어 해결하기 위한 인터페이스입니다. LOG는 append 중심의
원본 이벤트를, TAG는 태그 기반 계측값을, LOOKUP/RDB는 기준 정보를 담당합니다. 하나의
큰 서랍에 모든 것을 넣는 대신, 문서함, 측정함, 기준표를 나누어 두는 방식에 가깝습니다.

이렇게 나누어 두면 입력 경로와 조회 패턴도 명확해집니다. 원본 이벤트는 빠르게 쌓고, 태그
계측값은 시간축과 태그 이름으로 찾고, 기준 정보는 조인과 해석에 사용합니다. 시계열 시스템의
실제 가치는 이 세 가지가 함께 동작할 때 나타납니다.

## 문제 확인 예제

다음 예제는 이벤트형 데이터를 LOG 테이블에 저장하고 시간 조건으로 조회합니다. 장비
`pump01`이 특정 시각에 `OK` 상태였다는 작은 이벤트를 기록한 뒤, 같은 날짜의 이벤트를
다시 찾아보는 흐름입니다. 산업 IoT에서는 설비 상태 기록이 되고, 금융 시스템에서는 특정
종목의 틱을 수신했다는 이벤트 기록이 같은 패턴으로 저장될 수 있습니다.

```sql
CREATE TABLE DBMS_GS_EVENTS (
  EVENT_TIME DATETIME,
  DEVICE_ID VARCHAR(20),
  STATUS VARCHAR(20)
);

INSERT INTO DBMS_GS_EVENTS
VALUES (TO_DATE('2026-07-02 09:00:00', 'YYYY-MM-DD HH24:MI:SS'), 'pump01', 'OK');

SELECT DEVICE_ID, STATUS
FROM DBMS_GS_EVENTS
WHERE EVENT_TIME >= TO_DATE('2026-07-02 00:00:00', 'YYYY-MM-DD HH24:MI:SS');

DROP TABLE DBMS_GS_EVENTS;
```

위 SQL이 `/tmp/dbms_gs_events.sql` 파일에 저장되어 있다고 가정하고 다음 명령을 실행합니다.

```bash
machsql -s 127.0.0.1 -P 5656 -u SYS -p MANAGER -f /tmp/dbms_gs_events.sql
```

결과에 `pump01`과 `OK`가 보이면 이벤트 저장과 시간 조건 조회가 정상적으로 동작한 것입니다.
이 패턴은 장애 이력, 서비스 상태 변화, 보안 이벤트, 틱 수신 이력처럼 “언제 어떤 일이
있었는가”를 따라가야 하는 데이터의 출발점이 됩니다.
재실행 중 `DBMS_GS_EVENTS`가 이미 존재한다는 오류가 나면
`DROP TABLE DBMS_GS_EVENTS;`를 실행한 뒤 다시 시작합니다.
