Machbase DBMS는 데이터가 산발적으로 쌓이는 환경보다, 끊임없이 흘러 들어오는 환경에서 진가를 발휘합니다. 공장 설비의 상태 정보, 서비스 접속 로그, 도시 인프라의 센서 값, 금융 시장의 틱 데이터처럼 시간이 지날수록 빠르게 양이 불어나는 데이터가 그 대상입니다. 이런 데이터는 단순히 저장하는 것만으로는 부족합니다. 유입되는 즉시 확인할 수 있어야 하고, 나중에 언제든 다시 분석할 수 있어야 합니다.

시계열 데이터베이스가 해결하는 문제는 "많은 데이터를 저장한다"는 것에 그치지 않습니다. 데이터가 쏟아질 때 한 건도 놓치지 않아야 하고, 방금 들어온 데이터와 오래전에 쌓인 데이터를 모두 시간 조건으로 꺼낼 수 있어야 합니다. 원본 데이터를 오래 보관할수록 저장 공간도 그만큼 커지기 때문에, 어느 시점부터 집계 데이터로 전환하거나 보관 기간을 제어하는 운영 전략도 필수입니다.

Machbase DBMS는 다음 조건이 동시에 존재하는 환경에 적합합니다.

- 장비, 센서, 애플리케이션, 시장 데이터 피드에서 초 단위 이하로 데이터가 지속적으로 발생합니다.
- 최근 데이터는 즉각 조회해야 하고, 과거 데이터도 장기 분석에 활용해야 합니다.
- 높은 입력 성능을 유지하면서 SQL, 집계, 조인, 보관 정책을 함께 운용해야 합니다.
- 시계열 원본 데이터와 기준 정보를 한 시스템에서 다뤄야 합니다.
- 초·밀리초 단위 원본 데이터와 분·시간·일 단위 집계 데이터를 함께 관리해야 합니다.

테이블 유형은 이러한 문제를 역할별로 나누어 해결하기 위한 인터페이스입니다. LOG는 append 중심의 원본 이벤트를, TAG는 태그 기반 계측값을, LOOKUP과 RDB는 기준 정보를 담당합니다. 하나의 거대한 테이블에 모든 것을 밀어 넣는 대신, 이벤트 기록함·계측값함·기준표를 명확히 나누어 두는 방식입니다.

이렇게 역할을 분리하면 입력 경로와 조회 패턴도 자연히 명확해집니다. 원본 이벤트는 빠르게 쌓고, 태그 계측값은 시간축과 태그 이름으로 찾으며, 기준 정보는 조인과 해석에 활용합니다. 시계열 시스템의 실질적인 가치는 이 세 가지 역할이 함께 맞물려 동작할 때 비로소 나타납니다.

## 문제 확인 예제

다음 예제는 이벤트형 데이터를 LOG 테이블에 저장하고 시간 조건으로 조회합니다. 장비 `pump01`이 특정 시각에 `OK` 상태였다는 이벤트를 기록한 뒤, 같은 날짜의 이벤트를 다시 조회하는 흐름입니다. 산업 IoT에서는 설비 상태 기록으로, 금융 시스템에서는 특정 종목의 틱 수신 이벤트 기록으로 동일한 패턴이 반복됩니다.

```sql
CREATE TABLE DBMS_GS_EVENTS (
  EVENT_TIME DATETIME,
  DEVICE_ID VARCHAR(20),
  STATUS VARCHAR(20)
);

INSERT INTO DBMS_GS_EVENTS
VALUES (TO_DATE('2026-07-02 09:00:00', 'YYYY-MM-DD HH24:MI:SS'), 'pump01', 'OK');

SELECT DEVICE_ID, STATUS
FROM DBMS_GS_EVENTS
WHERE EVENT_TIME >= TO_DATE('2026-07-02 00:00:00', 'YYYY-MM-DD HH24:MI:SS');

DROP TABLE DBMS_GS_EVENTS;
```

위 SQL이 `/tmp/dbms_gs_events.sql` 파일에 저장되어 있다고 가정하고 다음 명령을 실행합니다.

```bash
machsql -s 127.0.0.1 -P 5656 -u SYS -p MANAGER -f /tmp/dbms_gs_events.sql
```

결과에 `pump01`과 `OK`가 출력되면 이벤트 저장과 시간 조건 조회가 정상적으로 동작한 것입니다. 이 패턴은 장애 이력, 서비스 상태 변화, 보안 이벤트, 틱 수신 이력처럼 "언제 어떤 일이 있었는가"를 추적해야 하는 데이터의 출발점이 됩니다. 재실행 중 `DBMS_GS_EVENTS`가 이미 존재한다는 오류가 나면 `DROP TABLE DBMS_GS_EVENTS;`를 실행한 뒤 다시 시작합니다.
