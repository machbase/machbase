Machbase DBMS는 산업 IoT 데이터와 금융 틱 데이터처럼 시간 순서로 지속적으로 유입되는 데이터를 빠르고 효율적으로 처리하기 위한 시계열 데이터베이스입니다. 공장의 컨베이어 벨트처럼 센서 값이 쉼 없이 들어오거나, 거래소 시세처럼 짧은 간격으로 가격과 거래량이 갱신되는 환경에서는 "어디에 저장하느냐"가 성능과 운영 편의성을 좌우합니다. Machbase DBMS에서의 첫 번째 설계 결정은 데이터 성격에 맞는 테이블 유형을 선택하는 것에서 시작합니다.

시계열 데이터는 크게 두 가지 형태로 나타납니다. 첫째는 센서가 1초마다 온도를 전송하듯 규칙적인 간격으로 들어오는 계측값이고, 둘째는 주문 체결·알람 발생·로그 기록처럼 사건이 발생할 때마다 생성되는 이벤트입니다. 실제 시스템에서는 두 형태가 공존합니다. 산업 IoT 환경에서는 설비의 온도와 진동이 계측값이고 알람과 정비 이력이 이벤트이며, 금융 시스템에서는 호가·체결 틱이 빠르게 유입되고 수신 상태·처리 지연이 이벤트로 기록됩니다.

## 먼저 구분할 테이블

| 테이블 | 주 용도 | 첫 선택 기준 |
| --- | --- | --- |
| LOG | 이벤트, 로그, 이력처럼 계속 append 되는 데이터 | 산업 장비 이벤트, 금융 틱 수신 이력처럼 입력량이 많고 시간 조건으로 자주 조회합니다. |
| TAG | 센서, 설비, 계측값처럼 태그 이름과 시간축이 있는 데이터 | 태그별 시계열 조회와 집계가 중심입니다. |
| LOOKUP | 코드, 장비 메타데이터, 매핑 정보 | 작고 자주 참조되는 기준 데이터를 빠르게 조인하거나 조회합니다. |
| RDB | 관계형 업무 데이터, 상태 데이터, 큰 기준/차원 데이터 | RDB 지원 버전의 Standard Edition에서 `CREATE RDB TABLE`로 만들며 행 단위 `INSERT`, `UPDATE`, `DELETE`와 다른 테이블 유형과의 조인을 지원합니다. |
| VOLATILE | 세션성 임시 데이터 | 서버 종료 시 사라져도 되는 메모리 데이터를 다룹니다. |

LOG와 TAG는 대량 시계열 입력을 위한 추가 중심 테이블입니다. `CREATE TABLE`에 별도 유형을 지정하지 않으면 기존 호환성을 위해 LOG 테이블이 생성됩니다. TAG 데이터 UPDATE 지원 버전에서는 태그 이름, 시간 조건, 데이터 컬럼 조건으로 대상 범위를 좁혀 값을 보정할 수 있습니다. 단, TAG 이름, 시간축, 시스템 컬럼 자체를 바꾸는 일반 행 수정으로 이해하면 안 됩니다. 일반적인 행 단위 수정이 중심인 업무 데이터라면 RDB, LOOKUP, VOLATILE 문서도 함께 검토합니다. RDB는 8.6의 Standard Edition v1 기능이며 Cluster Edition에서는 RDB 테이블 생성을 지원하지 않습니다.

테이블 유형은 역할별 저장 공간으로 이해할 수 있습니다. LOG 테이블은 시간 순서로 쌓이는 기록을, TAG 테이블은 센서 이름과 시간축 기준의 계측값을 담습니다. 설비 온도 값은 TAG 테이블에 자연스럽게 어울리고, "틱을 수신했다"는 이벤트 기록은 LOG 테이블에 맞습니다. 자주 참조하는 소규모 기준표는 LOOKUP에, 관계 제약과 업무 규칙이 중요한 데이터는 RDB 테이블에 두는 것이 명확합니다. RDB 테이블은 관계형 업무 데이터와 Machbase 시계열 데이터를 함께 다루는 용도로 이후 장에서 별도로 설명합니다.

시계열 DBMS를 설계할 때는 테이블 유형과 함께 데이터 수명주기도 반드시 고려해야 합니다. 최근 원본 데이터는 높은 해상도로 신속하게 조회해야 하지만, 오래된 데이터는 집계 형태로 보관해도 충분한 경우가 많습니다. 보관 정책, 롤업, 다운샘플링, 압축은 단순한 부가 기능이 아니라 저장 비용과 조회 성능을 결정하는 핵심 설계 요소입니다.

이 개요를 읽은 뒤에는 [10분 빠른 시작](../quick-start/)에서 LOG 테이블을 한 번 생성해 봅니다. 그 예제 하나로 `CREATE TABLE`의 기본 결과가 LOG 테이블이라는 점과 입력, 조회, 삭제 흐름을 함께 확인합니다.

## Machbase DBMS 소개

Machbase DBMS는 산업 IoT 데이터와 금융 틱 데이터 같은 시계열 데이터를 고속으로 처리하도록 설계된 시계열 데이터베이스입니다. 사용자는 익숙한 SQL로 테이블을 만들고 데이터를 조회하지만, 내부적으로는 테이블 유형에 따라 입력, 저장, 조회 특성이 다르게 동작합니다. 겉으로 같은 SQL처럼 보여도 어떤 테이블에 담느냐에 따라 데이터가 정리되는 방식이 달라집니다.

일반적인 업무 데이터는 특정 레코드를 정확히 찾아 수정하거나 여러 테이블을 조인하는 일이 중심입니다. 반면 시계열 데이터는 대부분 계속 추가되고, 시간 범위로 읽히며, 평균·최대·최소·합계 같은 집계를 통해 의미를 얻습니다. "지난 10분 동안 온도가 어떻게 변했는가", "장 마감 직전 틱이 얼마나 몰렸는가", "지난 한 달간 설비 알람이 어느 시간대에 집중되었는가"처럼 시간 흐름을 따라가는 질문이 시계열 데이터베이스의 본령입니다.

### 핵심 관점

- 데이터가 지속적으로 유입된다면 LOG 테이블을 먼저 검토합니다. 애플리케이션 로그, 이벤트 이력, 장비 상태 기록, 금융 틱 수신 로그가 대표적입니다.
- 태그 이름, 시간, 값의 구조가 명확하다면 TAG 테이블을 먼저 검토합니다. "어느 태그가, 어느 시각에, 어떤 값을 가졌는가"가 핵심인 온도 센서 값 같은 데이터에 적합합니다.
- 소규모의 조회 중심 기준 정보는 LOOKUP을 먼저 검토합니다. 장비 코드와 장비명의 매핑처럼 자주 참조하는 작은 기준표로 활용할 수 있습니다.
- 관계형 업무 엔터티와 변경이 중요한 기준 정보는 RDB 계열 문서를 검토합니다. RDB 테이블은 RDB 지원 버전의 Standard Edition에서 `CREATE RDB TABLE`로 생성합니다.
- 서버 재시작 시 소멸해도 무방한 임시 작업 데이터는 VOLATILE 테이블을 사용합니다.

이 관점은 Machbase를 처음 배울 때 특히 중요합니다. 시계열 데이터베이스의 기본 단위는 "현재 값 하나"가 아니라 "시간을 따라 이어지는 값의 흐름"입니다. 스키마를 설계할 때도 컬럼 목록만 볼 것이 아니라 입력 속도, 시간 조건, 집계 단위, 보관 기간, 기준 정보와의 관계를 함께 고려해야 합니다.

처음에는 모든 테이블 유형을 직접 만들어 볼 필요가 없습니다. [10분 빠른 시작](/dbms/getting-started/quick-start/)의 LOG 테이블 예제로 SQL 흐름을 확인한 뒤, 데이터 성격에 맞춰 TAG, LOOKUP, RDB, VOLATILE 문서를 차례로 읽으면 됩니다. `SHOW TABLES` 결과에 `_TAG_DATA_`처럼 밑줄로 시작하는 `KEYVALUE` 테이블이 보일 수 있는데, 이는 TAG 테이블을 위해 DBMS가 내부적으로 관리하는 테이블이므로 첫 설계 대상에서 제외합니다.

## Machbase가 해결하는 문제

Machbase DBMS는 데이터가 산발적으로 쌓이는 환경보다, 끊임없이 흘러 들어오는 환경에 적합합니다. 공장 설비의 상태 정보, 서비스 접속 로그, 도시 인프라의 센서 값, 금융 시장의 틱 데이터처럼 시간이 지날수록 빠르게 양이 불어나는 데이터가 그 대상입니다. 이런 데이터는 단순히 저장하는 것만으로는 부족합니다. 유입되는 즉시 확인할 수 있어야 하고, 나중에 언제든 다시 분석할 수 있어야 합니다.

시계열 데이터베이스가 해결하는 문제는 "많은 데이터를 저장한다"는 것에 그치지 않습니다. 데이터가 쏟아질 때 한 건도 놓치지 않아야 하고, 방금 들어온 데이터와 오래전에 쌓인 데이터를 모두 시간 조건으로 꺼낼 수 있어야 합니다. 원본 데이터를 오래 보관할수록 저장 공간도 그만큼 커지기 때문에, 어느 시점부터 집계 데이터로 전환하거나 보관 기간을 제어하는 운영 전략도 필수입니다.

Machbase DBMS는 다음 조건이 동시에 존재하는 환경에 적합합니다.

- 장비, 센서, 애플리케이션, 시장 데이터 피드에서 초 단위 이하로 데이터가 지속적으로 발생합니다.
- 최근 데이터는 즉각 조회해야 하고, 과거 데이터도 장기 분석에 활용해야 합니다.
- 높은 입력 성능을 유지하면서 SQL, 집계, 조인, 보관 정책을 함께 운용해야 합니다.
- 시계열 원본 데이터와 기준 정보를 한 시스템에서 다뤄야 합니다.
- 초·밀리초 단위 원본 데이터와 분·시간·일 단위 집계 데이터를 함께 관리해야 합니다.

테이블 유형은 이러한 문제를 역할별로 나누어 해결하기 위한 인터페이스입니다. LOG는 추가 중심의 원본 이벤트를, TAG는 태그 기반 계측값을, LOOKUP과 RDB는 기준 정보를 담당합니다. 하나의 거대한 테이블에 모든 것을 밀어 넣는 대신, 이벤트 기록함·계측값함·기준표를 명확히 나누어 두는 방식입니다.

이렇게 역할을 분리하면 입력 경로와 조회 패턴도 자연히 명확해집니다. 원본 이벤트는 빠르게 쌓고, 태그 계측값은 시간축과 태그 이름으로 찾으며, 기준 정보는 조인과 해석에 활용합니다. 시계열 시스템의 실질적인 가치는 이 세 가지 역할이 함께 맞물려 동작할 때 비로소 나타납니다.

이 장의 대표 예제는 이러한 문제 중 가장 작은 단위인 "이벤트 한 건을 저장하고 다시 읽기"만 확인합니다. 실제 설계에서는 먼저 데이터가 이벤트인지, 태그 기반 계측값인지, 기준 정보인지 구분한 뒤 해당 테이블 유형 문서로 이동합니다.
